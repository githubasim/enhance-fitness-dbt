# PT analytics with dbt and DuckDB

A portfolio project that models a fictional personal-training fitness chain in Dubai.
All data is synthetic, generated by the scripts in `generator/`. No real company data is used.

## Stack
Python (pandas, numpy) for generation, DuckDB as the local warehouse, dbt Core with
dbt-duckdb for transformations, Git for version control.

## Layers
| Layer | Models | Purpose |
|---|---|---|
| raw | 7 tables | CSVs loaded as-is, with a `_loaded_at` column for freshness checks |
| staging | `stg_*` (7) | One model per source table: types and names only |
| intermediate | `int_sessions_enriched` | Joins sessions, packages, payments and trainers; revenue and commission rules |
| marts | `dim_*`, `fct_*`, `mart_*` (12) | Star schema plus metric tables for dashboards |

## Metric definitions
- **Price per session**: net package price divided by sessions included.
- **Recognised revenue**: delivered and no-show sessions, excluding refunded packages. Cancelled and booked sessions earn nothing.
- **Commission**: trainer commission rate times price per session, on delivered sessions only, calculated on net price.
- **Margin**: recognised revenue minus commission.
- **Utilisation**: delivered hours divided by available hours (weekly availability x 52 / 12), counted from the later of trainer hire date and club opening date. The current partial month is excluded.
- **Idle hours**: available hours minus delivered and no-show hours.
- **Retention**: share of a first-purchase cohort with at least one delivered session in a given month.
- **Renewal rate**: share of matured packages followed by another purchase by the same client.

## Quality checks
71 dbt tests: unique, not_null, relationships, accepted_values, plus custom tests for
revenue reconciliation between fact tables, pricing grain, and capacity. Source freshness
is configured on all raw tables. Two tests warn by design:
- sessions scheduled before the assigned trainer's hire date (about 3%): flagged, not removed
- trainer-months where delivered hours exceed available hours

## Known limitations
- The data is synthetic with fixed probabilities, so renewal rates and discount effects carry no real signal.
- Clients are allocated to clubs by room count regardless of opening date, so utilisation varies unrealistically by club (Palm above 100%, Al Barsha below 50%).
- Cancelled sessions are never rebooked, so packages look under-used.
- Retention is session-based and mixes package expiry with churn.
- Commission is assumed to be paid on net price and only on delivered sessions; these would need confirming with Finance.
- Runs on DuckDB only. I have not run this on a cloud warehouse.

## Run it
```
conda create -n enhance-dbt python=3.12 -y
conda activate enhance-dbt
pip install dbt-duckdb pandas numpy
.\run_all.ps1
dbt docs generate
dbt docs serve
```
